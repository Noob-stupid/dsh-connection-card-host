## 0. 目标（用户原话精神）

把**普通 DSH 插件**作为卡片挂到连接上 —— 例如 A 端挂 Blender 建模能力、B 端挂逻辑整理能力：

1. **能力按端生效**：只对该连接、该端的会话可见可用
2. **全局 UI 不出现**：这些插件本来会全局注册 UI，适配后不允许出现在 DSH 全局界面
3. **UI 捕获进面板**：它们的 UI 应被捕获、渲染进 **[连接] 面板**（面板左右两侧留白处）
4. **不破坏既有隔离承诺**：卡片系统不与 DSH 内部结构耦合，DSH 升级不破坏我们的宿主与协议

用户定位（原话意译）：

> 我们这套是**脱离于全局、只效忠于卡片挂载**的，那它们的 UI 就应该只显示在连接面板里。

### 0.1 范围界定（用户明确）

| 类别 | 例子 | 是否纳入 | 理由 |
|:--|:--|:--|:--|
| **全局增强 / 能力型插件** | Blender 建模、逻辑理解整理…… | **纳入** | 这正是诉求：挂到连接上、**卡片能调用**、完全活在面板里 |
| **主题 / 装饰型插件** | 皮肤中心、宠物…… | **不纳入** | 用户**不会**在连接面板里注册这类；它们的作用域本就是全局观感 |

**这条界定的作用**：适配层的目标不是"让任意 DSH 插件都能塞进面板"，而是
**让能力型插件成为卡片的能力来源**。装饰类的捕获没有意义（它的价值就在于全局观感），
写进协议可以避免以后把范围无限扩大。

> 补充：官方 UI 指引本身就要求插件"容器与控件**继承宿主主题**"（F9）——
> 也就是说主题是**宿主层的事**，不该由卡片层去接管。这与上表一致。

## 1. 已核实的事实

每条都带出处；未核实的一律标为待验（见 §6）。

### F1 —— 卡片运行时**物理上 import 不到** `@deepseek-ai/*`（决定性）

`src/card-host/sandbox.ts` 的 `importCardModule` 是裸的动态 `import(url)`：**没有解析钩子、没有路径注入**。
卡片目录在 `$DSH_HOME/connection-cards/cards/`，Node 从那里逐级向上找 `node_modules`，**DSH 的包不在解析路径上**。

⇒ 普通 DSH 插件的宿主入口**原样塞进卡片运行时连加载都过不了**（模块级 `import … from '@deepseek-ai/…'` → `ERR_MODULE_NOT_FOUND`）。

> **✅ 已用真运行验证（不再是推理）** —— 同一份探针文件（`import { Context } from '@deepseek-ai/cordis'`）：
>
> | 位置 | 结果 |
> |:--|:--|
> | 卡片那种目录（外层无 `@deepseek-ai`） | ❌ `Cannot find **package** '@deepseek-ai/cordis'` |
> | 干净对照（profile 目录，包可解析） | ✅ `ok= function` |
>
> **唯一差别就是解析路径** —— 结论成立。
>
> ⚠️ 过程留痕：第一版"对照"选在了我们自己的包目录里，结果**也失败**。
> 查错误消息才发现是**两回事**：那是 `Cannot find **module** …/cordis/lib/index.js`
> —— 包找到了，但那个 junction 指向的是**源码检出**（`lib/` 里只有 `types/`，没有 `index.js`）。
> 即"对照位置无效"，不是结论错误。换成 profile 目录后对照成立。
> **教训**：探针也要自查；只看 `e.code` 会把"包找不到"和"入口文件不存在"混为一谈。

**这条把"透明直通"从"我们不选的方案"变成"不存在的路"** —— 除非主动加 module resolution 钩子把 DSH 包映射进卡片解析链，而那等于在隔离墙上开洞。
**所以适配只能是申报制（见 §3 护栏②），没有第二个选项。**

> 附带结论：插件把 `@deepseek-ai/*` **vendor 进自己包里** = 双实例脱节（自己的 loader / 事件总线与活实例不同源，表现为"注册了工具但谁也调不到"）—— **明确不支持**，写进能力矩阵。

### F2 —— 调用时校验的通道已验证存在

`src/tools/awareness-tools.ts`：`exec.agent`（`ToolExecutionInput.agent`，"set by the agent loop"）就是调用者身份。
我们自己的 5 个工具全靠 `callerSessionId(exec)` 认调用者，认不出时返回明确失败文案。

⇒ 护栏③要求的"执行入口再校验 scope"**有现成先例**，不是新机制。

### F3 —— 生命周期的收口模式已有

`src/index.ts`：`tools.register(def)` 返回 disposer，挂到 `ctx.effect(() => () => disposeTools())`。
⇒ 适配层工具同样持有 disposer，绑定三处：`unloadCard` / 连接删除 / `restoreAll` 重放前先清。

### F4 —— 按会话改写工具面 / 注入提示的瀑布

`src/core/tool-scoping.ts`：`ctx.on('system-prompt/assemble', async (assembly, context, next) => …)`，
`context.scope.session.id` 就是会话 id —— 摘工具、**加提示块**都在这一处。整个模块 fail-open（拿不准就原样下发）。

### F5 —— 卡片的按端可见性模型已存在

`src/card-host/loader.ts`：scope `a` / `b` / `both` 已贯穿工具列举（`listCardTools`）与调用校验（`callCardTool`，拒绝文案区分"卡片对你不可见"与"没这个工具"）。

### F6 —— 卡片 UI 的现状

`src/ui/CardStack.tsx`：宿主侧 `renderPanel(api)` 产出 **HTML 字符串** → 面板内 `dangerouslySetInnerHTML`。
即：卡片 UI 今天是**静态 HTML**，没有事件绑定、没有活状态。

### F7 —— **客户端插件的真实形态**（官方模板 + 我们自己的 bundle 双向确认）

官方模板 `templates/decoration/client.js`：

```js
window.__ModuleLoader__.load({
  id: '@local/my-decoration',
  factory(require) {
    const React = require('react');
    return { inject: ['slots'], apply(ctx) { ctx.slots.register({…}, Decoration) } };
  },
})
```

我们自己的 `lib/client.js` **同一形状**（id = 包名，`factory: (require) => …`，内部 `require("react")`）。

⇒ **factory 就是一个普通函数，返回 `{ inject, apply(ctx) }`** —— 这意味着**可以由我们给它一个影子 ctx**（§4）。

### F8 —— 客户端清单段

`package.json` 的 `dsh.client`：`{ platform, inject: [...], external: [...] }`。
我们自己的：`inject: ['@deepseek-ai/dsh-client-runtime', '@deepseek-ai/dsh-client-ui-slots']`，`platform: 'web'`。
官方说明：React 等来自**浏览器模块表**，"不要重复安装 React / 不要 CDN / 不要 UMD 查找"；非基线运行时依赖在 `dsh.client.external` 声明。

### F9 —— 官方对 UI 插件的硬约束（写协议时要遵守）

- **不要替换 app root、不要往 `document.body` 追加第二个应用**
- 不要读别的插件的 DOM / 样式 / 组件源码来估算位置；**选已经分配了空间的槽位**
- 资源（样式、定时器、监听）在 `apply` 里用 `ctx.effect` / `ctx.on` 注册并返回清理函数
- 文案走 Client locale 服务；容器与控件继承宿主主题

> ⚠️ 我们自己的 `overlay-host.ts` 是往 `body` **追加了一个 div**（0×0、`pointer-events:none`）——
> 它不是"第二个应用"，但与 F9 的字面表述相邻。**记录在案**：若官方口径收紧，这是需要复议的点。

## 2. 决策（用户裁决）

| 编号 | 问题 | 裁决 |
|:--|:--|:--|
| **D1** | v1 是否给适配卡 `llm` 能力 | **给** |
| **D2** | 同一插件挂多条连接时工具注册份数 | **单份注册 + 按调用者会话动态解析**（避免注册表膨胀） |
| **D3** | UI 方向 | **捕获并渲染进 [连接] 面板**（不是"以后再说"）——落点：**面板左右两侧留白处** |
| **D4** | 挂载方式 | **C 混合**：垫片层（B）覆盖"能不能加载"，适配器（A）兜底"要什么运行环境" |
| **D5** | 功能范围 | **插件原有功能全部保留，不减功能** —— 它对会话有什么功能，适配后就还有什么；卡片代码同样能调用 |

### 2.1 D5 的准确含义（用户原话精神）

> 不就是用户需要增强的能力能直接挂载卡片脱离于 DSH 吗，它本身有什么对会话的功能，
> 那种插件本来的功能都可以有啊。

即：**适配不是"降级"，是"换个宿主"** ——
插件原本给会话提供的一切（工具、事件、状态、提示贡献）都照旧存在，
差别只在于**作用域从全局收窄到这条连接 / 这个端**，以及** UI 落在面板里而不是全局**。

所以"卡片能调用"不是额外需求，而是 D5 的自然结果：卡片是编排者，它当然要能驱动自己挂载的能力，
**会话里的模型**同样要能调用 —— 两条路都通。

## 3. 三条护栏（与对端讨论的结论）+ 两条补充

### 护栏① —— 隔离承诺必须分层表述

「DSH 升级不破坏我们」这条承诺**分三层**，不能说成一句：

| 层 | DSH 升级时 |
|:--|:--|
| 卡片**系统**（宿主 / 协议 / 面板） | 承诺不变：只依赖稳定面 |
| 普通卡片 | 不受影响（不 import DSH 内部） |
| **适配卡** | **引入插件自身的 DSH 耦合**，失效模式与"全局安装该插件"相同 —— 但坏在卡片里：崩溃隔离兜底、一键可卸、不波及 DSH |

可适配 / 不可适配的判据（**硬判据来自 F1**）：

- **可适配**：作者（或我们）为它写了**申报制适配器**；纯能力型；无全局副作用；声明了兼容范围
- **不可适配**：模块级 import `@deepseek-ai/*`（F1：加载都过不了）；vendor DSH 副本；`ctx.set` 全局服务 / 监听全局事件 / 写配置 / 开定时器 / 注册命令 / 依赖 client 服务

### 护栏② —— 影子 ctx = **能力申报制 + 显式失败**

清单形态草案：

```yaml
dshCard:
  adapter: './adapter.js'                      # 薄适配器，不 import 任何 @deepseek-ai/*
  capabilities: ['tools', 'prompt', 'llm']     # 申报的能力 = 审计面
```

影子 ctx **只实现申报的能力**；访问未申报能力 → **apply 当场抛错**，错误信息列出可用能力。

为什么是"显式失败"而不是另两种：**放行** = 全局副作用照样发生（"脱离全局"不成立）；**静默忽略** = 插件拿不到服务莫名崩溃、难查。
第三条路是把边界变成**加载期错误**，让问题在装上的一刻就暴露。

能力候选集：`tools` / `prompt` / `llm` / `events` / `state`（后两者 v1 是否给，见 §6）。

### 护栏③ —— 调用时校验 + 生命周期绑定

- **调用时校验**（F2）：适配工具的 `execute` 里 `callerSessionId(exec)` → 查该会话是否在该卡片 scope 端 → 不在则拒绝。
  拒绝文案学 `callCardTool`：说清"**这张卡片对你不可见**"，而不是"找不到工具"。
- **生命周期绑定**（F3）：disposer 绑定 `unloadCard` / 连接删除 / `restoreAll` 重放前先清 —— 不留幽灵工具。

### 补充④ —— 工具命名空间

全局注册表撞名是真实风险（两张卡都注册 `search`）。
适配层**强制前缀注册**：`card_<cardId>_<tool>`，schema 描述里注明所属卡片。

### 补充⑤ —— 多连接共享（已按 D2 定案）

单份注册；execute 时按调用者会话动态解析到具体连接 / 卡片实例。

## 4. UI 捕获机制草案（基于 F7 / F8）

> **这是本次最重要的方向修正。** 早前我把 UI 重定向判为"高风险、v2 再说"，
> 依据是"要造影子 slots ctx + 解决组件互操作"。**F7 推翻了这个判断的一半**：
> 客户端制品的接口是一个**普通工厂函数**，不是需要 DSH 加载器才能实例化的黑盒。
> 剩下真正难的不是**加载**，而是**服务依赖**（见风险 R3）。

**四步：**

1. **取源码**：宿主侧已持有插件包目录（安装后）→ 把 `lib/client.js`（或 `dsh.client` 指向的制品）源码文本经 RPC 送到浏览器。
   （面板已经在用这条 RPC 通道取卡片 HTML，通道现成。）
2. **影子 ModuleLoader 捕获 factory**：在页面里**临时替换** `window.__ModuleLoader__` 为捕获桩，执行该源码 →
   拿到 `{ id, factory }`，然后**立刻还原**。全局注册表全程不被污染。
3. **影子 ctx（护栏②）**：调 `factory(require)` 得到 `{ inject, apply }`，再以**我们构造的 ctx** 调 `apply`：
   - `require` **复用 DSH 交给我们的同一个模块表**（F8：同一 React 实例，不会重复安装）
   - `ctx.slots.register/inject` → 我们的 facade，把 `{name, id, key}, Component` **捕获进我们自己的注册表**
   - 只提供申报能力；未申报的访问 → 抛错
4. **渲染 + 收口**：捕获到的 Component 渲染在 **[连接] 面板左右两侧留白处**；
   facade 记录 disposer，面板卸载时统一清理（F9 的资源纪律）。

**为什么成立（三条）：**

- `factory` 是普通函数（F7 双向确认）
- `require` 可复用我们的模块表 → 同一 React 实例 → 组件能在我们的树里正常渲染
- **我们的面板本身在 DSH provider 树内** → 捕获组件仍继承主题与上下文

**风险 / 待验（R 系列，见 §6）：**

- **R1** 其他插件的构建产物是否都严格同形（我们只验证了两个样本，生态多样）
- **R2** 源码执行方式（`new Function` vs 注入 script）在不同 CSP 下是否都可行
- **R3**（最难）插件可能依赖 `inject` 里声明的其它客户端服务（locale / store / session 状态）。
  facade 要么代理真服务，要么**明确拒绝捕获**并说清缺什么 —— **不做"忽略后祈祷不崩"**
- **R4** 组件的**交互**（点击、表单）在捕获后是否仍能正确工作（依赖真值的服务最容易在这里暴露）
- **R5** 默认不捕获：**必须有卡片显式申报**才捕获，否则全局 UI 依旧不出现（回到"不加载 client 入口"的 v1 行为）

### 4.1 垫片层（B）的兼容性边界 —— 一处**纠正**

早前我把 B 描述成"插件用到垫片范围外的东西就会崩"，暗示兼容性很差。**这个说法不准确，纠正如下。**

**关键点：垫片可以 `re-export 真模块`，不必造假对象。**

我们自己的插件就声明并解析着真 DSH 包（`package.json` peers）：

```
@deepseek-ai/cordis               >=4.0.1 <4.1.0
@deepseek-ai/dsh                  >=0.2.0-rc.1 <0.3.0
@deepseek-ai/dsh-client-ui-slots  >=0.2.0-rc.1 <0.3.0
@deepseek-ai/dsh-client-runtime   >=0.2.0-rc.1 <0.3.0
```

我们**运行在 DSH 进程内**，因此垫片文件可以 `export * from '<真模块解析路径>'` ——
ESM 按 URL 缓存，**插件拿到的就是同一批模块实例**，不是副本。这消除了 B 的大半兼容顾虑。

**B 真正解决不了的（这些不是"模块找不找得到"，而是"运行环境与依赖图"）：**

| # | 缺口 | 层次 | A 能否兜 |
|:--|:--|:--|:--|
| B1 | `ctx.inject(['X'])` 依赖**别的插件提供的服务**，而那些插件没挂 | 依赖图 | ✅ 但需一并声明依赖 |
| B2 | 插件声明了**非打包的 npm 依赖**（安装器只拷目录、不装依赖） | 安装层 | ✅ 需补依赖安装 / 要求打包 |
| B3 | 插件刻意做**全局副作用**（注册全局设置页、监听应用启动、写配置） | 语义 | ⚠️ 只能拦或拒（护栏②） |
| B4 | **版本偏斜**：垫片给的是"今天的"真模块，插件按别的版本构建 | 版本 | ❌ 与全局安装同种失效，无法兜 |
| B5 | **客户端侧**：捕获到的 factory 需要 `require` 到其它客户端包 | 运行时 | ⚠️ React 没问题；其余需代理或明确拒绝 |
| B6 | 插件依赖 **loader 提供的运行环境**（config schema、行配置、启停生命周期） | 运行时 | ✅ 由适配层提供等价物 |

⇒ **C 的界线因此很清楚**：
**垫片管"能不能加载"，适配器管"要什么运行环境"。**
B 覆盖得越广，需要写适配器的插件越少；超出 B 的部分**明确拒绝并说清缺什么**，而不是祈祷不崩。

## 5. 调研计划

**三个问题（对每个候选插件）：**

1. 它用了哪些 `ctx.*` 接口？有没有全局副作用？
2. 它注册的工具能否在**调用时**校验会话 scope？
3. 它是否声明了兼容的 DSH 版本范围？

**对象修正**：调研普通插件入口**不再**是为了"直接塞进影子 ctx"（F1 已堵死这条路），而是为了：

- 提炼**能力清单候选集**该长什么样（哪些能力是能力型插件的真需求）
- 产出**能力矩阵**：插件 / 需申报的能力 / 薄适配器工作量 / 是否纯工具型 / 是否可捕获 UI
- **试点选择**：优先**我们自己或对端有源码的纯工具型插件** —— 能同时写卡片版与全局版做对照验证

**产出物**：协议草案（`docs/card-protocol.md` 新增"DSH 插件适配"章节：适配形态、能力清单、命名规则、生命周期、责任边界、**回退**）→ 与对端对齐 → 再动手写代码。
